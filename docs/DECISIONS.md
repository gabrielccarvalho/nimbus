# Architecture decision records

Format: context → decision → consequences. Append new ADRs; supersede, don't edit, old ones.

## ADR-0001: Next.js App Router, installed version (16.4)

Context: the project was scaffolded with Next 16.4.6. Decision: App Router, Server Components by default, `"use client"` only at leaves. Consequences: APIs follow the bundled docs in `node_modules/next/dist/docs/`, not older habits.

## ADR-0002: TypeScript strict + noUncheckedIndexedAccess

Context: lots of array indexing over words, samples and segments. Decision: `strict`, `noUncheckedIndexedAccess`, no `any`, `unknown` + zod at boundaries. Consequences: some extra narrowing in hot loops, fewer runtime surprises.

## ADR-0003: shadcn/ui on the existing preset (base-nova, Base UI)

Context: the preset uses Base UI (`@base-ui/react`), not Radix. Decision: the shadcn-first rule; custom primitives build on Base UI and use its `render` prop where Radix would use `asChild`. Consequences: Radix-only snippets from the web don't apply directly.

## ADR-0004: Phosphor icons

Context: `components.json` sets `iconLibrary: phosphor`. Decision: use `@phosphor-icons/react` everywhere. Consequences: generated components already match.

## ADR-0005: zod for every boundary

Decision: shared schemas for forms, actions, API, env, settings and LLM output. Consequences: one source of truth for types via `z.infer`.

## ADR-0006: react-hook-form + zod resolver for forms

Decision: settings and clip editing forms use react-hook-form with `@hookform/resolvers/zod` and the shadcn field components. Consequences: forms submit to Server Actions that re-validate.

## ADR-0007: SQLite + better-sqlite3 + Drizzle

Context: local-first, zero infra. Decision: SQLite file in `DATA_DIR`, WAL mode, foreign keys on, drizzle-kit migrations, repositories per feature. Consequences: synchronous driver (fast, simple). Postgres later means a new schema dialect and repositories, callers unchanged.

## ADR-0008: Local disk storage behind StorageAdapter

Decision: files under `DATA_DIR` (default `./data`, gitignored), addressed by keys. Consequences: an S3 adapter can implement the same interface and contract tests.

## ADR-0009: DB-backed job queue

Context: no Redis wanted. Decision: `jobs` table with atomic leasing (`UPDATE … RETURNING`), heartbeats, exponential backoff, lease recovery. Consequences: throughput is limited by SQLite writes, which is far beyond what video jobs need.

## ADR-0010: Separate worker process via tsx

Decision: `worker/index.ts` run with tsx; `pnpm dev` runs Next and the worker with concurrently. Consequences: Next requests stay fast and independent of ffmpeg; two processes share SQLite (WAL handles it).

## ADR-0011: SSE for progress, polling fallback

Decision: `/api/projects/[id]/events` polls the DB inside the request and pushes changes as SSE. Consequences: no cross-process pub/sub needed; latency ≈ 500 ms.

## ADR-0012: System ffmpeg via spawn, no fluent-ffmpeg

Decision: pure argument/filtergraph builders plus a thin runner. Consequences: everything is golden-testable as strings; the runner owns timeouts and cancellation.

## ADR-0013: Transcriber interface; whisper.cpp default, fake for tests

Decision: whisper.cpp CLI with full JSON output for word timestamps. Consequences: model path and binary come from env; `pnpm run doctor` checks them.

## ADR-0014: Three highlight selectors

Decision: Anthropic (structured tool output, model from `ANTHROPIC_MODEL`, default `claude-opus-5-5`), Manual (copy prompt, paste JSON) and Heuristic (no LLM). Shared post-processing enforces the hard rules for all three. Consequences: works offline; LLM output can never bypass the rules.

## ADR-0015: Cache Components off; per-request reads via `connection()`

Context: Next 16 offers `cacheComponents`. This is a single-user local app whose data changes constantly from a second process. Decision: leave it off; query functions call `await connection()` so pages render per request; actions call `revalidatePath`. Consequences: no stale data, no cache invalidation across processes.

## ADR-0016: `server-only` and the worker

Context: `server-only` throws unless resolved under the `react-server` condition. Decision: run the worker with `tsx --conditions=react-server`, alias it to an empty module in Vitest. Consequences: the same server modules work in Next, the worker and tests.

## ADR-0017: Webcam detection in the browser

Decision: MediaPipe Tasks Vision face detector (WASM) on sampled proxy frames plus a pure border heuristic, confirmed by the user. Optional Claude vision check behind a setting. Consequences: no server GPU or Python; detection is testable through the pure heuristic.

## ADR-0018: ASS subtitles burned with libass

Decision: generate ASS with word-level highlight and burn with the `ass` filter. Consequences: requires an ffmpeg with libass (not present on the dev machine at bootstrap; see PROGRESS Blockers).

## ADR-0019: Horizontal edit via trim/atrim + concat

Context: `select`/`aselect` drops whole audio frames and drifts across many cuts. Decision: one trim/atrim pair per kept range plus `concat`, graph passed via `-/filter_complex <file>`. Consequences: sample-accurate cuts; large graphs live in a file, not argv.

## ADR-0020: pino logging

Decision: structured pino, pretty in dev, silent in tests. Consequences: logs carry `projectId`/`jobId` context.

## ADR-0021: Testing stack

Decision: Vitest (unit, component, integration, contract), RTL, MSW, Playwright + axe. Fixtures generated with ffmpeg lavfi. Consequences: no binary fixtures in git; tests need ffmpeg.

## ADR-0022: Quality tooling

Decision: existing ESLint + Prettier (tailwind plugin), husky + lint-staged pre-commit, GitHub Actions CI. Consequences: CI installs ffmpeg via apt.

## ADR-0023: Work on a feature branch

Context: the repo had only `master`. Decision: build on `build/auto-clipper`, commit per task group. Consequences: `master` stays at the initial scaffold until the user merges.

## ADR-0024: `pnpm run doctor`, not `pnpm doctor`

Context: pnpm 11 ships a built-in `pnpm doctor` that shadows the package script. Decision: keep the script name `doctor` and always invoke it as `pnpm run doctor`. Consequences: docs and CI use `pnpm run doctor`.

## ADR-0025: E2E against a production build on port 3217

Context: port 3100 was taken locally; dev-mode compilation makes e2e timing flaky. Decision: Playwright builds and starts Next on `E2E_PORT` (default 3217) and starts the worker as a second webServer, both with a fresh temp `DATA_DIR` per run. Consequences: e2e runs take a build (~30 s) but behave like production.

## ADR-0026: Structured outputs, not forced tool use, for Claude selection

Context: current Claude models reject forced `tool_choice` (`any`/`tool`) with a 400, and `messages.parse()` throws on an unparseable reply before `stop_reason` can be checked. Decision: call `beta.messages.create` with `output_config.format = betaZodOutputFormat(schema)`, check `stop_reason` first (refusal → heuristic fallback, `max_tokens` → repair turn), then validate with the format's own `parse()`. Default model `claude-opus-5-5` at effort `high`, with `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) so a classifier refusal is retried on another model server-side. Consequences: one code path for validation; the heuristic always produces a result.

## ADR-0027: Worker and scripts load env files like Next

Context: Next loads `.env*` files, but the worker (`tsx worker/index.ts`) and `pnpm run doctor` didn't, so `.env.local` settings such as `FFMPEG_PATH` or `ANTHROPIC_API_KEY` reached the web app but not the process that uses them. Decision: `lib/load-env.ts` calls `@next/env`'s `loadEnvConfig` (pinned to the installed Next version) as the first import of every Node entrypoint. Consequences: identical precedence in web and worker; variables already set in the process (e.g. by Playwright) still win.

## ADR-0028: ffmpeg-full for libass

Context: Homebrew's `ffmpeg` has no libass, so captions can't be burned in (Blocker B1). Decision: use the keg-only `ffmpeg-full` formula via `FFMPEG_PATH`/`FFPROBE_PATH` in `.env.local`; the system `ffmpeg` is untouched. Consequences: `pnpm run doctor` fails the libass check if the paths are missing, and the README documents the setup.

## ADR-0029: Blocking metadata

Context: Next 16 streams `generateMetadata` output into `<body>` after the first paint, so dynamic pages briefly have no `<title>` (caught by axe as an intermittent `document-title` violation). Screen readers announce the title on load. Decision: `htmlLimitedBots: /.*/` makes metadata blocking for every request. Consequences: slightly later first byte; irrelevant here because metadata is a local SQLite read.

## ADR-0030: Vision assets served locally

Context: MediaPipe loads its WASM and model at runtime; the default is a CDN. Decision: `pnpm run setup:vision` copies the WASM from the pinned `@mediapipe/tasks-vision` package and downloads `blaze_face_short_range.tflite` once into `public/vendor/mediapipe` (gitignored). Consequences: detection works offline after setup and always matches the installed package version; e2e runs the setup before building.

## ADR-0031: Bundled caption fonts

Context: libass falls back to whatever system font matches, so captions would look different per machine, and the app fonts come from `next/font` at build time, which ffmpeg can't use. Decision: commit static ExtraBold TTFs of the two design-system families (Oxanium, Nunito Sans; SIL OFL, licenses in `assets/fonts/licenses`) and pass `fontsdir`. The preview uses the same families via the `--font-heading`/`--font-sans` variables. Consequences: deterministic renders from a clean clone; ~135 KB in the repo.

## ADR-0032: libx264 by default, hardware encoding opt-in

Context: VideoToolbox/NVENC/QSV are much faster but their quality-per-bit and rate-control knobs differ per vendor, and CRF output is predictable and identical across machines. Decision: `VIDEO_ENCODER=libx264` by default; `auto` or an explicit encoder name opts in. Capabilities are detected from `ffmpeg -encoders` and shown by `pnpm run doctor`. Consequences: consistent output by default; a 30 s 1080×1920 clip still renders in a few seconds with `veryfast`.

## ADR-0033: Tests load `.env.test.local`, never `.env.local`

Context: integration tests need machine-specific binaries (e.g. an ffmpeg with libass) but must never pick up personal settings like `ANTHROPIC_API_KEY` from `.env.local`. Decision: the integration setup imports `lib/load-env`, and because Vitest runs with `NODE_ENV=test`, `@next/env` loads `.env.test.local`/`.env.test` only. Consequences: put `FFMPEG_PATH`/`FFPROBE_PATH` in `.env.test.local` (gitignored); caption burn-in tests are skipped when the configured ffmpeg has no libass.

## ADR-0034: Streamed, uncompressed zip export

Context: rendered clips are already H.264/AAC, so deflate saves almost nothing and costs CPU, and a zip of several clips can be hundreds of MB. Decision: `GET /api/projects/[id]/export` streams a zip built with `yazl` in STORE mode straight from storage, names files `NN-<title-slug>.mp4` plus `edit-horizontal.mp4`, and adds a `clips.json` manifest (title, hook, range, `editedSinceRender`). Renders missing on disk are left out instead of failing the download. Consequences: constant memory, no temp files; a clip edited after rendering still exports its last render, and the manifest flags it.

## ADR-0035: Editing a rendered clip marks it out of date

Context: trims, text and caption edits change the output, but throwing away a good render on every save would be surprising. Decision: saving an edit moves a `rendered` clip back to `approved` and keeps `renderAssetId`; the UI shows "Out of date" and offers "Save and render". Changing the trim clears per-page caption overrides because page indices no longer line up. Consequences: downloads stay available while editing; "Render approved clips" picks up edited clips again.

## ADR-0036: Env sets defaults, Settings override

Context: some options (selector, transcription language, hardware encoding) were env-only, which means editing a file and restarting to change them. Decision: one `settings` row holds app settings; `getAppSettings` fills anything unsaved from env (`HIGHLIGHT_SELECTOR`, `WHISPER_LANGUAGE`, `VIDEO_ENCODER !== "libx264"`). Highlight and caption options are copied into each new project; language, render quality (CRF 26/20/17) and hardware encoding are read when a job runs. `VIDEO_ENCODER` still chooses which hardware encoder "on" means. The unimplemented "verify layout with Claude" flag was dropped from the schema. Consequences: no restart needed; existing projects keep their own highlight and caption settings.

## ADR-0037: Media route serves an allowlist, not all of `DATA_DIR`

Context: the media route served any key that resolved inside `DATA_DIR`, which included `app.db`, partial uploads and render work files. Decision: `isServableKey` allows only `projects/<id>/<file>` and `projects/<id>/renders/<file>` with video, audio or JPEG extensions; anything else is a 404 before storage is touched. Traversal protection in `LocalStorage.resolve` stays as a second layer. Consequences: new servable asset types must be added to the allowlist.

## ADR-0038: Drain rejected upload bodies instead of cancelling them (workaround)

Context: Next 16.4's request body adapter (`requestToBodyStream`) keeps calling `controller.enqueue` after the body is cancelled, which surfaced as an `uncaughtException: Invalid state: ReadableStream is already closed` whenever an upload was rejected mid-stream (wrong magic bytes, over the limit). Decision: uploads read the body through `readableFromRequestBody`, which drains and discards the rest of a rejected body rather than cancelling it. This is a workaround; the proper fix is upstream in Next (guarding enqueue after cancel), after which `Readable.fromWeb` can return. Consequences: a rejected upload keeps reading until the client stops sending; the client sees the error once its request completes or it aborts.

## ADR-0039: Every landscape source goes through layout; a fill mode for Shorts

Context: the app is used to turn 16:9, 4:3 and 21:9 recordings into YouTube Shorts in volume. 4:3 was classified `other`, which forced blur-fill and skipped webcam detection, and there was no full-screen option for recordings without a webcam. Blur-fill also assumed the source was wider than 9:16. Decision: classify `4:3` and `16:10` too; route any source with `w ≥ 1.2 h` through `awaiting_layout`; add `no-cam-fill` (a 9:16 gameplay crop steered by the focus slider); fit the blur-fill foreground inside the frame. Add "Approve all" for bulk review. Layout presets per resolution remain the way to skip the layout step for repeat setups. Consequences: one more layout mode in the renderer, preview and caption baselines, all through `planLayout`.

## ADR-0040: Import from a link with yt-dlp as a pipeline step

Context: creators want to make Shorts from videos already on YouTube without finding the original file. Decision: a `download` job and `downloading` status ahead of `probe`, behind a `Downloader` port with a yt-dlp adapter and a fake for tests (same pattern as the transcriber). The link is stored on the project (`projects.source_url`) so retry needs no payload. yt-dlp is optional: `doctor` warns when it's missing and uploads are unaffected. Alternatives: downloading inside the request (blocks it for minutes), or a JS YouTube library (breaks whenever YouTube changes; yt-dlp is maintained against those changes and covers Twitch and other sites too). Consequences: one more status and migration; YouTube's terms limit downloading, so the UI tells users to import only videos they own or have rights to.

## ADR-0041: Postgres in Docker instead of SQLite

Context: the app is moving from a single-user tool towards something more standard to run and eventually host. SQLite serialised writers, so the worker and Next contended on one file lock, and a second worker process wasn't practical. Decision: Postgres 17 via Docker Compose (only the database; Next and the worker stay on the host for VideoToolbox and whisper's Metal acceleration). The queue leases with `FOR UPDATE SKIP LOCKED`. Unit and integration tests use PGlite so they run without Docker; one race test and the e2e suite use the compose server. Existing SQLite data is copied once with `pnpm db:import-sqlite`. `LISTEN/NOTIFY` for SSE was considered and dropped: the stream still has to read the snapshot on each change, and one indexed query per open tab every 500 ms is negligible. Consequences: Docker is needed to run the app; every repository is async, and code inside `withTransaction` must use the transaction handle; `DATA_DIR` is now created by the storage layer, since the database no longer lives in it.

## ADR-0042: Per-project settings and spoken-language detection

Context: one global settings row meant changing a language or clip length for one stream changed it for every later one, and whisper's language detection only listened to the first 30 s, which on a stream is often game audio. A Portuguese streamer playing an English game was transcribed as English. Decision: every pipeline setting lives on the project (language, voice track, selector, clip lengths, count, captions, render quality); global settings are defaults copied into new projects, and imports can override language and selector. Hardware encoding stays global because it depends on the machine. Changing a setting offers to re-run the earliest affected step; the state machine allows idle projects back into `transcribing` or `selecting`, and candidate replacement keeps approved and rendered clips. Language is the explicit setting, else the video page's language (yt-dlp), else a probability-weighted vote over 7 windows of 30 s across the recording. The default whisper model becomes the multilingual `large-v3-turbo-q5_0`. Alternatives: whisper's own detection (first 30 s only), or detecting per segment and transcribing each in its own language (much slower and splits the transcript). Consequences: ~5 s of detection per transcription; English-only models can't serve non-English streams, and `doctor` warns about them.

## ADR-0043: Language-independent highlight scoring

Context: the heuristic counted a fixed list of English words and scored loudness and speech density against the whole video, so a Portuguese stream got no keyword credit and a loud game section outranked a real reaction elsewhere. Decision: score every signal against the surrounding two minutes (loudness spike, speech-rate jump, laughter and exclamations, repeated words, pause before the peak, question and answer), add reaction phrases from per-language data files plus per-project catchphrases, and count phrases and exclamations only above 1.5× the streamer's own rate so verbal tics don't count. Low word confidence scales the score down, which mostly catches game dialogue in another language. The Claude selector is told the language and splits multi-hour transcripts into overlapping parts sent in parallel. Alternatives: translating the English list (still misses slang and tics), or asking Claude for every stream (needs a key and costs per stream). Consequences: weights are set by hand and checked on one real stream; they should be revisited once there are streams with known good moments.

## ADR-0044: Step details on the job row

Context: the overview only showed a percentage, so a long transcription or download looked frozen. Decision: each step reports a small typed detail object, stored in `jobs.detail` and sent in the existing polled SSE snapshot, rather than a separate event channel or table. The worker writes it with the heartbeat (at most every 500 ms), so detail updates cost no extra writes, and flushes it before completing. Payloads are capped (transcript tail ~400 characters, 240 waveform points, 300 silences, 30 candidates) because every open tab polls the snapshot twice a second. Alternatives: LISTEN/NOTIFY or an append-only events table (finer grained, but more moving parts for one local user), or reading partial outputs from disk in the request (couples the web app to each tool's files). Consequences: a step that finishes in under 500 ms may never show its detail, which is fine because its result appears right after.

## ADR-0045: Stall timeouts instead of fixed job timeouts

Context: each job type had a fixed wall-clock limit (probe 10 min). A 7-hour upload failed three times in probe because transcoding the preview proxy takes longer than that, even though ffmpeg was progressing. Separately, expired leases were only recovered when a worker started, so a job orphaned by a worker that died after another had started stayed "running" forever. Decision: a job fails when it reports no progress for a per-type limit (10–30 min), with a 24 h cap on total run time; lease recovery runs every lease interval. Alternatives: scaling fixed limits by media duration (needs the duration before probe has read it, and still guesses machine speed). Consequences: a step that does long work without reporting progress must report it, or it will be stopped.

## ADR-0046: Caption only the streamer's language, and clear captions in pauses

Context: on Portuguese streams of GTA 6, the burned-in captions included the game's English dialogue, and whisper hallucination loops (the same line every second for minutes; 922 of 2381 segments on one stream). Whisper also stretched words across the pause after them (up to 7 s), so captions stayed on screen through silences. Decision: filter at caption time, not in the stored transcript, so existing transcripts benefit without re-transcribing hours of audio. A segment is dropped when more of its words are function words exclusive to another language (pt, en, es, fr, de, it lists) than function words of the transcript's language; languages without a list are not filtered. Repeats of a line said 3+ times in a row are dropped, keeping the first. Each word's visible time is capped by its length, and page gaps and hold are shorter. Alternatives: whisper language detection per segment (minutes of extra work per stream), a language-ID package (couldn't be added here, and models trained on long text are weak on 2–5 word lines), or speaker diarization (the real fix for game dialogue in the streamer's own language, but a heavy Python dependency). Consequences: dubbed game dialogue in the streamer's language is still captioned; short English interjections from the streamer are dropped; per-clip caption page edits are indexed by page, so clips edited before this change may need their caption text checked.

## ADR-0047: YouTube replay heatmap as a highlight signal

Context: imports from YouTube come with "Most replayed" data, which yt-dlp already returns in the details the download step fetches. Decision: store it on the project (`audience_heatmap`, `null` = not fetched yet, `[]` = the video has none) and use it as a 0.2-weight signal in the heuristic and as a hint in the Claude prompt, never as a filter. It is scored on its own 0–1 scale above the median rather than rescaled like the other signals, and the weighted sum is normalized so projects without it score as before. Older imports get it the next time highlights are selected; if the site refuses (bot checks, rate limits), selection continues without it and tries again next time. The review timeline shows it as a band along the top. Alternatives: the YouTube Data API (doesn't expose the heatmap and needs a key), or using the heatmap to pick clips directly (buckets are 1% of the video, minutes long on a stream, and replays don't always mean a good Short). Consequences: only popular YouTube videos have it; a fresh upload or a Twitch VOD won't, so it's a bonus rather than something the selector relies on. The 0.2 weight hasn't been tuned on real heatmaps yet.

## ADR-0048: Caption font picker with locally installed fonts

Context: users want to pick the caption font independently of the preset, including Pricedown, whose Typodermic desktop EULA allows rendered video but not redistributing the font file. Decision: `font` is a caption style override over a fixed registry (`CAPTION_FONTS`); every font file lives flat in `assets/fonts` (libass doesn't scan subfolders). OFL fonts are committed; Pricedown is gitignored and installed by hand. Pages pass the installed fonts to the picker, which disables missing ones, `pnpm run doctor` warns about them, and the browser preview loads non-`next/font` families from `/api/fonts/[font]`. Consequences: a clean clone still renders with the bundled fonts; a style saved with Pricedown on a machine without the file falls back to libass's default font, which doctor flags.

## ADR-0049: Indigo and highlighter-yellow rebrand

Context: the near-black + lime palette and Oxanium/Nunito pairing read as a generic gaming-tool template, and the Projects page was a stack of default blocks. Decision: indigo ink surfaces and a highlighter yellow `primary` that only marks what the pipeline found (clip ranges, the spoken word) and primary actions; Archivo for all UI text, condensed through its `wdth` axis for headings. The Projects page lists recordings as rows with a read-only `Timeline` showing every clip's position in the VOD. Caption fonts load from `/api/fonts/[font]` so the preview no longer depends on UI fonts. Consequences: the caption highlight is now yellow and the outline indigo ink (golden ASS updated); `highlight-ink` exists for readable yellow text on light surfaces; radius drops to 8 px.

## ADR-0050: yt-dlp cookies for YouTube's bot check

Context: YouTube answers anonymous yt-dlp requests from some IPs with "Sign in to confirm you're not a bot". We reported it as rate limiting and retried, which can't succeed and keeps hitting YouTube. Decision: opt-in `YTDLP_COOKIES_FROM_BROWSER` / `YTDLP_COOKIES`, passed to every yt-dlp call; the bot check maps to `DEPENDENCY_MISSING` (no retries) with a message naming the setting, and doctor warns when neither is set. Consequences: imports run as the signed-in browser profile; reading Chrome's cookies on macOS can show a Keychain prompt the first time.

## ADR-0051: Steer highlights away from cutscenes

Context: on GTA 6 streams the selector kept picking cutscenes and story moments (the streamer commenting on a phone call, a kidnapping scene) instead of fights, chases and loud reactions. Whisper transcribes the game's dialogue, so cutscenes look like dense, dramatic speech; the prompt rewarded "a reaction, a joke, a strong opinion" without saying what to avoid. Decision: three layers. The prompt now ranks action with a loud reaction first and lists what not to pick. The transcript gives Claude two cutscene hints: game dialogue stretches (bins dominated by another language's function words) and runs of hard camera cuts, from a new ffmpeg scene-detection pass over the proxy (~10 s per hour) stored in `signals.cuts`. Post-processing multiplies every selector's score by `1 − 0.6 × game-dialogue coverage`, and the heuristic counts only the streamer's words for speech rate, excitement and repetition. Alternatives: HUD or letterbox detection (GTA 6 cutscenes have no bars, and HUDs differ per game), motion energy (needs a full decode at higher resolution, and cutscene cameras move too), or penalizing camera cuts directly (on our streams chases and mission-fail screens cut as often as some cutscenes, so cuts are only a hint). Consequences: on two reviewed GTA 6 streams, a dry run picked no cutscenes and 5 of the 10 previously approved clips; the misses were calm moments (golf, rants, the map reveal), which now rank lower by design. Game dialogue in the streamer's own language isn't detected, so those streams rely on camera cuts and the prompt. Projects analyzed before this change have no cuts until analysis runs again.

## ADR-0052: Claude watches candidate frames, and clips start on the payoff

Context: short-form retention was very low. Claude picked clips from the transcript and audio signals alone, so it couldn't see what makes GTA clips work (bugs, physics chaos, crashes); on the transcript a glitch looks like any other "what?? bro". The prompt also asked for clips to start a few seconds before the action, which is where Shorts viewers swipe away. Decision: two passes. The transcript pass over-fetches (3× the clip count, at most 40) as recall. A visual pass sends 12 frames per candidate from the proxy (with 3 s of lead-in) plus its transcript to Claude, which re-scores it by what's on screen and moves the start to the payoff; its score replaces the first pass's. A per-project niche (preset profiles, auto-detected from the title) tells both passes what hooks viewers in that game. The review model is `ANTHROPIC_REVIEW_MODEL`, defaulting to `ANTHROPIC_MODEL` (Opus). A failed review keeps the first pass, marked on each clip, rather than failing the step. Alternatives: a better transcript prompt only (still blind to glitches), sending video (not supported by the API; frames are the equivalent), a motion-energy signal (doesn't tell a glitch from a cutscene camera move), or free-text niches (no built-in tuning; may come later as extra instructions). Consequences: roughly 100–150k extra input tokens per stream on Opus; selection takes longer (6 parallel requests after the first pass). The heuristic selector doesn't get the review or payoff starts. There's no retention data yet, so the frame count, pool size and scoring rubric are untuned guesses to revisit once posted clips have numbers.

## ADR-0053: Clip effects render through sendcmd-driven scale and crop

Context: zoom and shake change a region's crop every frame, and the render has to match the browser preview, which draws `frameAt` live. `crop` only re-evaluates x/y per frame and works in whole pixels. Decision: `effectCommands` samples `frameAt` once per output frame and writes a `sendcmd` file. Each region crops its fixed layout rect, then `scale@eN` resizes that rect so the current crop lands at the destination size, and a fixed-size `crop@eN` picks the offset. Commands are only written on frames where a value changes. Focus is a full-frame webcam branch overlaid with `enable='between(t,…)'` at half-frame edges, and its crop gets the same shake commands. Spike (cam-top, 1920×1080 testsrc2 fixture, 30 fps, 30 s with zooms, shakes and two focus ranges): plain graph 3.37 s on videotoolbox and 2.42–2.54 s on libx264; this mechanism 3.35–3.40 s (1.0×) and 2.81–3.02 s (1.1–1.25×). Sampled frames land within 0.5 output px of `frameAt`, on the right frame. Alternatives: `sendcmd` driving `crop` w/h/x/y on a ×2 upscaled input matched as closely but cost 1.3–1.4× on libx264, because every frame is upscaled even when nothing moves; `zoompan` with piecewise `if(between(on,…))` expressions was 2–4+ px off during shakes and fails to parse past a few hundred segments, so a 30 s clip wouldn't render. Consequences: clips with effects use a separate graph (`features/render/effects-graph.ts`); clips without keep `verticalGraph` and its goldens. `scale` re-initialises swscale whenever its size changes, which is cheap at these sizes. `sendcmd` refuses an empty file, so it is left out when no crop ever moves. The output frame rate is applied before the split, so commands are timed to output frames.

## ADR-0054: Clip effects share one frame function

Context: Shorts that hold attention cut to the streamer's face on a reaction, punch in on the game when something weird happens and shake on a scream. Clips used one fixed layout for their whole length. Effects have to be placed automatically, fixable by hand, and look the same in the browser preview as in the render. Decision: a clip stores `effects: { events, edited } | null` with three kinds (focus, zoom, shake) at absolute source ms, and a pure `frameAt(layout, source, events, t)` returns the crop rects for any time; the canvas preview draws it and the render samples it per frame into `sendcmd` (ADR-0053). A pure planner places events at selection from loudness, speech rate and optional "beats" that the visual review marks on frames it already sees (no extra calls); beats are stored on the clip so planning again is free. Tracks stay auto until the user edits them; "Reset to auto" returns a plan without saving (`planClipEffectsAction`) so unsaved edits elsewhere in the editor survive. The Clips page became a grid of 9:16 tiles with a dialog player that previews effects before rendering. Alternatives: a full-game focus kind (the stacked layout already shows the game), effects that move captions (they stay on the final frame), ffmpeg-only previews (a render per tweak), or placing effects from Claude alone (heuristic projects would get none). Consequences: `effects = null` renders byte-for-byte as before, so existing goldens hold. A layout without a webcam keeps its focus events but ignores them. The planner constants are guesses until checked on real streams. Addendum (2026-11-23): full game was added after all, as `focus` with `target: "game"` (default `"cam"`, so stored tracks parse unchanged): the no-cam-fill crop fills the frame on webcam layouts, zoom applies inside it, the render overlays it as a second slot, and only the user places it. Each focus target in use adds a full-resolution branch for the whole clip, so a clip with both pays for two. The clip repository parses `effects` with `clipEffectsSchema` on read (unparseable values read as null), so stored focus events without `target` reach every consumer as `"cam"`.

## ADR-0055: The gameplay box is stored in `gameplayRect`

Context: the dashed gameplay box was display-only, moved sideways by a "Gameplay focus" slider in the layout step, and couldn't be changed per clip. Decision: the box is a second crop region in both editors, shape-locked to the slot it fills and stored in the existing `gameplayRect`. A rect already at the slot's shape passes through `coverCrop` unchanged, so there's no schema or render change; an edit resets `gameplayFocusX` to 0.5 so full game shows the centre of the box. The slider is removed. The editors show the stored rect when it is within 1% of the slot's shape and only derive the box from `coverCrop` otherwise, because re-deriving it from even pixels on every render made it creep. The render still cover-crops that stored rect to the slot, so the editor box and the rendered crop can differ by up to ~1% (plus even-pixel rounding). Alternatives: a free-shape box (the render would cover-crop it and silently cut what the user framed) or new offset and zoom fields (duplicating `gameplayRect`). Consequences: untouched layouts render as before, including after a mode switch: a mode switch only refits a box the user has edited (one already at its slot's shape), around its centre with the same area, and a box at full height or width stays at the largest size the new slot allows.

## ADR-0056: Nimbus reads Dia's cookies itself

Context: the bot check (ADR-0050) needs signed-in cookies, and exported cookies.txt files go stale when YouTube rotates the session. The daily browser here is Dia, which yt-dlp's `--cookies-from-browser` can't decrypt: it looks for Chrome's Keychain entry, not "Dia Safe Storage". Decision: `parseBrowserSpec` claims `dia` (optionally `dia:<profile>`); before each yt-dlp call Nimbus copies the profile's `Cookies` DB, reads the youtube.com and google.com rows with the system `sqlite3`, decrypts them with the Keychain key (PBKDF2 "saltysalt", AES-128-CBC, schema 24's 32-byte host hash stripped) and passes a 0600 temporary cookies.txt via `--cookies`, deleted when the call ends. The key is cached for the process. Any other browser name still goes to yt-dlp unchanged. Alternatives: a manual cookies.txt export (goes stale), Safari or Firefox (a second browser to keep signed in), or a yt-dlp plugin (more moving parts than one small module). Consequences: cookies are read fresh on every import, so nothing needs refreshing while Dia stays signed in. macOS asks once for Keychain access ("Always Allow"). It's macOS-only and depends on Dia keeping Chromium's cookie format; a format change shows up as the bot-check error again.

## ADR-0059: Accounts with Better Auth, one personal workspace each

Context: the redesign adds sign-in, a workspace with a plan and usage, connected channels and a per-workspace Claude key; until now Nimbus had no users and one global settings row. Decision: Better Auth (email and password, optional Google and Twitch, TOTP two-step with backup codes) on the existing Drizzle/Postgres database, with its tables in `lib/db/schema.ts`. Signing up creates a personal workspace ("<first name>'s studio"); projects get a `workspace_id`, and the first workspace ever created claims the projects and the settings row from before accounts. Workspace defaults live in the settings table under `workspace:<id>`. `proxy.ts` only checks that a session cookie exists; every page, server action and route checks the session itself (`requireViewer`, `forProject`, `assertProjectAccess`), and another workspace's project reads as not found. `/api/uploads` is left out of the proxy because a proxy buffers request bodies and truncates them past 10 MB. The Claude key is stored AES-256-GCM encrypted with `NIMBUS_SECRET_KEY`, shown only as `sk-ant-…last4`, and preferred over `ANTHROPIC_API_KEY`. Usage is a `usage_events` row per render (seconds) and per Claude run, summed per UTC month against plan numbers that aren't enforced yet. Channels are Better Auth linked accounts: YouTube is Google with the YouTube scopes, Twitch is the Twitch account, and their tokens never leave the server; TikTok and Instagram show as not configured. Password reset writes the link to the server log, since Nimbus sends no email. Alternatives: Auth.js (no built-in two-step or session listing), a hand-rolled session table (more security surface to own), or keeping one global settings row (two accounts would share defaults). Consequences: every existing route needs a session, and Playwright signs up a user in a setup project and reuses its storage state. Teams, invites, billing and limits are out of scope; the plan numbers are placeholders. Losing `NIMBUS_SECRET_KEY` makes stored Claude keys unreadable, so they'd have to be entered again.

## ADR-0060: The clip editor saves as you go

## ADR-0061: Admin plan for nimbus.dev accounts

## ADR-0062: Profile photos and workspace logos

Context: people want their own photo and a logo for the workspace. Decision: the browser crops the chosen image to a square and re-encodes it at 256 px (WebP, or PNG where the browser can't encode WebP), then a server action stores it under `avatars/users/<id>/` or `avatars/workspaces/<id>/` with a timestamped name and saves `/api/avatars/…` in `user.image` or the new `workspaces.image`. The server accepts PNG, JPEG or WebP by their magic bytes, up to 512 KB, and deletes the previous file. `/api/avatars` serves a photo only to its owner and a logo only to its workspace. Deleting an account removes both. Alternatives: resizing on the server (needs an image library; ffmpeg would work but is heavy for this), or storing images in the database (bloats every user query). ## ADR-0064: Captions placed by hand

Context: the four position presets don't fit every layout, and people want to drop captions exactly where they look right. ## ADR-0065: Clips publish to YouTube from a hosted Nimbus

Context: people want to publish a rendered clip to their channel and later see how it did, which means Nimbus calls Google's APIs and, as a hosted service, serves many workspaces from one Google Cloud project. Google's current rules, read on 2026-11-24: `videos.insert` costs 1 unit in its own bucket of 100 calls a day, separate from the 10,000 units a day shared by every other endpoint (the bucket split took effect 2026-06-01, and the cost fell from about 1,600 units in late 2025); quotas reset at midnight Pacific; videos from unverified API projects are no longer locked to private since 2026-11-02, so there is no forced `privacyStatus` or error to handle; an OAuth app in "Testing" status gets refresh tokens that expire after 7 days; a Short can be up to 3 minutes. Not confirmed: whether the 100 uploads a day bucket applies after OAuth verification and the audit, how many named test users Testing mode allows (the spec says 100), and that `invalid_grant` is what an expired Testing-mode token returns (Google's page documents it only for revoked and policy-ended sessions). Decision: Google APIs are the second outbound dependency after Anthropic. One Google Cloud project serves every workspace, so Nimbus keeps a quota ledger in two buckets (uploads against `YOUTUBE_DAILY_UPLOADS`, default 100; everything else against `YOUTUBE_DAILY_QUOTA`, default 10,000), keyed to the Pacific day, and a publish that doesn't fit waits for the reset. Nimbus refreshes Google access tokens itself from the stored refresh token and treats `invalid_grant` as "needs reconnect". Calls to YouTube use `fetch` with the resumable upload protocol. Alternatives: the `googleapis` package (a large dependency for four endpoints, and it hides the upload offset we need to resume from), per-workspace Google Cloud projects (each user would have to create one), or no ledger and relying on Google's 403 (a burst of publishes would fail instead of queueing). Consequences: public launch needs Google's OAuth verification and the YouTube API audit, tracked as blocker B4; until then Testing mode makes channels drop off every 7 days. Sources: the YouTube Data API revision history and quota cost pages, and Google's OAuth 2.0 token expiration docs.

## ADR-0066: Published clip stats and the channel playbook

Context: once a clip is on YouTube, people want its numbers next to it, and later to learn from them. Google's rules, read on 2026-11-24: `videos.list?part=statistics` costs 1 unit from the shared daily bucket; the YouTube Analytics API (`youtubeanalytics.googleapis.com/v2/reports`) has its own quota whose limit isn't documented; analytics data lags 48 to 72 hours; the retention curve is `elapsedVideoTimeRatio` with `audienceWatchRatio` (about 100 points, values can exceed 1), and a report with no rows omits the `rows` key; a deleted video comes back as empty `items` or as a 404 `videoNotFound`. Not verified: whether YouTube returns retention for Shorts at all, and how long YouTube's developer policies allow analytics data to be stored (an audit item under blocker B4). Decision: the worker syncs a publication's stats at 1, 2, 7 and 28 days after `publishedAt` (`STATS_SYNC_AGES_DAYS`), checking for due syncs every 30 minutes, with never two `sync_stats` jobs for one publication; the clip dialog's "Refresh stats" enqueues one on demand. Each sync stores a `publication_stats` snapshot (views, likes, comments, average view duration and percentage, retention curve). Only the `videos.list` call is booked in the quota ledger (kind `stats`), because the Analytics quota can't be mirrored without a documented limit. Both removal shapes mark the publication `removed`, which drops it from stats lists. A missing or empty retention curve is normal and never an error; stats up to 72 hours old show "Data still coming in". The publication stores the uploaded range (`clip_start_ms`, `clip_end_ms`) so later phases can map retention back to the source. Google access tokens are now refreshed once per call (`withGoogleToken`) rather than once per job, so a sync that spans several calls re-checks expiry each time. Alternatives: syncing on page view (a request would wait on Google, and hosted traffic would burn quota), polling daily forever (quota for little new data after four weeks), or booking Analytics calls against a guessed limit. Consequences: until B4 passes, stats come only from Testing-mode channels, and storing analytics beyond a policy window may need a purge job.

Addendum (Phase 32): Claude analyzes a channel's published clips (`analyze_performance`, no project) and returns pending suggestions to add, edit or retire a playbook rule. A new analysis replaces the pending suggestions and keeps rejected ones. Approving a suggestion creates an immutable rule; editing creates a new rule that supersedes the old one, and retiring only sets its status. Restoring a retired rule flips its status back, with no new row, and the 12-rule cap per target still applies. Rule changes are serialized per channel with an advisory lock (`lockChannel`) and a suggestion is decided atomically, so two clicks can't exceed the cap or approve one suggestion twice. Edit and retire cards show the rule they change. Active rules go into the selection and review prompts as a "What has worked on this channel" block, only when rules exist, and each clip records the rule ids it was picked under (`playbookRuleIds`); clips pasted in manual mode don't record provenance. Rule ids are recorded only when the rules were actually applied: selection rules when Claude picked the clips without falling back, review rules when the visual review ran. Migration 0013 backfilled `clip_start_ms`/`clip_end_ms` from each clip's range at migration time, so a Phase 30 clip trimmed after publishing maps its retention slightly off. One analysis counts as one Claude run with no project. Consequences: no suggestion changes a prompt until a person approves it, and clips made before the first rule have no provenance.

## ADR-0067: Analytics for every Short on the channel

Context: ADR-0066 only tracked clips published from Nimbus. People want one place for the whole channel: Shorts posted outside Nimbus, channel totals and how a Short compares with the rest at the same age. Google's rules are as in ADR-0065 and ADR-0066: `playlistItems.list`, `videos.list` and `channels.list` cost 1 unit each from the shared daily bucket, a page holds at most 50 items and `videos.list` takes at most 50 ids; Analytics data lags 48 to 72 hours; Developer Policies III.E.4 let Analytics data be kept while other Authorized Data (`videos.list` statistics and snippets) must be refreshed or deleted within 30 days. Decision: a publication can exist without a clip. `publications.origin` is `nimbus` or `imported`, `clip_id` is nullable, and `channel_id` now cascades, so a channel's publications and their daily rows go with it (no code path deletes a channel row except workspace deletion). `sync_uploads` walks the uploads playlist, and `sync_channel` reads channel daily metrics (`docs/PIPELINE.md`). Short detection: there is no Shorts flag in the Data API, so a video is a Short when its duration is 1 to 180 s, unless a per-video `creatorContentType` probe through the Analytics API answered, in which case `SHORTS` wins (`VIDEO_ON_DEMAND` is long, anything else other). Against the fake the probe path ran; on a real channel it hasn't been confirmed, and when the probe fails the import falls back to duration for the rest of the run. Import cost: one `channels.list` for the playlist id, then per page one `playlistItems.list` plus one `videos.list` for the ids not already known, all booked under kind `import`. A first run walks the whole playlist; later runs skip known ids and stop after the first page that holds a video older than the last sync minus 7 days, except a manual import, which reads every page. When the quota is spent the job re-enqueues itself for the reset with its page token and the pass's start time, which becomes the new watermark. Daily data: `publication_daily` (views, minutes watched, likes, subscribers gained per Short and day) and `channel_daily` (views, minutes watched, average view duration, likes, comments, shares, subscribers gained and lost). Columns are read by header name; days a successful call omits count as 0 views. Because of the lag, ages and periods end at the last day with data. A Short's data end is `min(dataThrough, max(lastStoredDay, pacificDay(dailySyncedAt) - 3))`, so omitted zero-view days inside a successful call's range count as 0, while the last three days stay open. `publications.daily_synced_at` records the last successful daily read; Shorts without daily rows (those published before this phase) get a bounded backfill, one attempt per Short per 24 h, so a daily read that keeps failing retries once a day rather than on every sweep. The same-age ratio replaces the sync-age buckets of Phase 31 (this closes that parked minor): a Short's cumulative views at age N, capped at 28 days, over the median of the other Shorts' cumulative views at that age, with no ratio under 2 days or with fewer than 3 peers. Refresh cadence: Nimbus Shorts keep days 1, 2, 7 and 28; after 28 days, and for every imported Short, a sync is due every 28 days, which re-reads `videos.list` data (titles included) inside the 30-day rule. A private or deleted imported Short becomes `removed`, while a Nimbus upload that turns private stays `published`. Publishing a clip deletes an imported row with the same channel and video id in the same transaction, under the same channel lock the import holds while it inserts, so a Short never lists twice. Insights lists Nimbus clips first, so imported Shorts don't crowd them out of the analysis, and the analysis prompt now says "clip or Short ids" because imported Shorts can be cited as evidence. Reconnecting a different YouTube channel drops the old channel's imports (their rows would belong to the wrong channel). The old `/channels` tabs had no URLs, so only `/channels?tab=insights` style links redirect to `/analytics/...`. Alternatives: a clip-less table separate from publications (two lists to merge everywhere), duration alone for detection (misses Shorts over 60 s that YouTube classes as Shorts since 2024), or fetching every Short's daily data on each sync (a call per Short per run). Consequences: the Shorts table, the overview and Insights read one set of rows. Final review fixes: the channel read falls back to an unsplit (`other`) report only when YouTube rejects the `creatorContentType` dimension, and each sync replaces its day range in one transaction, so a 403 or 429 can no longer leave unsplit rows beside split ones. A channel sync also refreshes the daily curve of every Short up to 31 days old (Analytics only), so young Shorts don't wait for the day 7 or 28 sync. "Top Shorts this period" comes from one Analytics top-videos call (50 videos) per period per channel sync, stored in `channel_top_videos` and joined to the channel's published Shorts, instead of summing sparse daily rows. Imported Shorts re-sync in `sync_stats_batch` jobs of up to 50 ids per `videos.list` call (1 unit a batch; a missing id means removed), deduplicated against single and batch jobs; Nimbus Shorts keep single jobs. A daily sweep enforces the 30-day rule when refreshes fail: snapshots older than 30 days are deleted and imported titles not refreshed in 30 days are blanked ("Untitled Short"); Analytics tables are kept. A worker shutdown between import pages hands the page token to a new job, any probe error other than an authorization failure falls back to duration, a failed channel job waits 6 h before the due sweep retries that type, and a channel switch cancels its queued channel jobs. Parked: a Short whose daily backfill keeps failing retries once a day indefinitely; the probe path is still unverified on a real channel; the `/channels?tab=…` redirects carry the query string along (`/analytics/insights?tab=insights`), which the pages ignore. Unresolved: a channel swap still leaves older Nimbus publications on the reused channel row, so refreshing those fails or reads another channel's video (parked since Phase 32). If YouTube's data lag exceeds 3 days, a few trailing days read as 0 until the next sync corrects them. Not verified: the 50-id cap of `videos.list` (the fake enforces it, a real call hasn't been made), the probe and `creatorContentType` together with channel subscriber metrics on a real channel, and the Analytics API's quota cost model (its calls aren't booked).

## ADR-0068: Music and on-screen text

Context: people want their own music under a clip and the hook burned in as a title, previewed in the editor before they render and publish (spec Phase 34). There is no API to attach YouTube's Shorts sounds, so the music has to be mixed into the file, and Nimbus can't check rights. Decision: tracks live in a workspace `music_tracks` table (title from the file name, editable; stored file; `durationMs`; created by). Uploads go to `/api/uploads/music`, streamed to disk with a 50 MB cap; the proxy matcher already skips `/api/uploads`, so the body isn't buffered. The format is sniffed from the first bytes (mp3, AAC/ADTS, m4a, wav, ogg, flac) and the stored extension comes from the sniff, not the file name. Our call: the upload request itself runs one ffprobe (it rejects files without an audio stream and gives the duration) and one streamed 8 kHz mono decode that folds into 240 waveform peaks, stored once. A track is at most 50 MB, so both are bounded, and the picker needs the duration and peaks right away; a job would leave a just-uploaded track unusable for a few seconds. `clips.audioMix` and `clips.textOverlay` are nullable jsonb, and null renders exactly as before. dB values are whole numbers (music −30…0, default −16; original −30…+6, default 0), fades are 0–5 s (by default no fade in and a 1.5 s fade out), and the overlay text defaults to the hook cut at a word to 80 characters with "…", or the title when there is no hook, or "Title" when both are empty. Empty text fails the save with "Add the on-screen text or turn it off", shown under the text field too. In the save payload a missing `audioMix` or `textOverlay` clears it (`.nullable().default(null)`, like `layoutOverride`); the editor is the only caller and always sends both fields. Ducking comes from the transcript, never a sidechain, so loud game audio can't pump the music: `planAudio` takes the clip's words made clip-relative with `wordsInRange(words, clip.startMs, clip.endMs)`, ends each word at the captions' `spokenEnd`, so a stretched Whisper word doesn't hold the duck through a pause, merges gaps under 400 ms, so the 200 ms ramps never overlap, and lowers the music 10 dB under speech. The envelope is one `volume=…:eval=frame` expression, which steps once per audio frame (1024 samples at 48 kHz, about 21 ms). The graph seeks the music input with `-ss trackStartMs`, `atrim`s it to the music length, applies volume, the envelope and `afade`s, and mixes it with the source at `sourceDb` through `amix=…:normalize=0`, followed by `alimiter=limit=0.95:level=0`. The limiter only catches clipping (a +6 dB source plus music can exceed full scale), and `level=0` keeps it from normalising, at the cost of slightly coloured loud peaks. There's no looping: when the clip outlasts the rest of the track the music stops early, and both fades are fitted into what the track has left. The overlay is one extra ASS event on layer 1 in its own `Title` style: bold, 1.2× the caption size (capped at 192), wrapped by libass (`\q0`) inside 90 px side margins, 240 px from the top or centred, from 0 to `untilMs` (default 3 s) or the whole clip. It needs libass even with captions off, with its own failure message ("This ffmpeg can't burn in on-screen text (no libass). Install one with libass or remove the text."). The track id lives in jsonb, so a foreign key can't block a delete. Instead, delete takes the track `FOR UPDATE` and refuses while any clip uses it, naming the clips, and a save that sets a track takes it `FOR SHARE`, so the two serialise. A track that was deleted, or belongs to another workspace, when a render starts fails the render with `CONFLICT` ("This clip's music track was deleted. Pick another track or remove the music."). `CONFLICT` is retryable, so the job is retried with backoff before the clip turns `failed`, the same as the other precondition errors. Any change to either field makes a rendered clip `approved` again, so the publish dialog says "Render the latest edit first". When a clip has a track, the dialog shows a Content ID warning under Privacy. In the editor, switching to a track the current start doesn't fit resets the start to 0, because the server rejects `trackStartMs ≥ durationMs`. The preview plays the track through Web Audio at `musicGainAt()` of the render's own plan, and routes the video through a gain only once the `AudioContext` is running, so a suspended context never silences the video. After that, every play resumes a context the browser suspended. The music pauses while the video buffers (`waiting`, or `readyState` below `HAVE_FUTURE_DATA`) and realigns on `playing`. The audio element is keyed by track, so a track change or unmount disconnects the music's source and gain; the video's route is never disconnected, since that would mute it. The preview doesn't apply the render's `alimiter`, so a loud mix can sound clipped in the editor but not in the file. The horizontal edit (`render_edit`) gets no music. Alternatives: sidechain compression (pumps with game audio), a worker job for the upload's probe and peaks (the track would be unusable for a few seconds), `loudnorm` or amix normalisation (changes the source level people set), looping the track (audible seams without beat matching), and a `music_track_id` column with a foreign key (the mix belongs in one jsonb value like the other clip edits). Consequences: the mix is fully deterministic, and golden graphs pin it. Real-ffmpeg checks in `tests/integration/render.test.ts` measure the 880 Hz band to prove the mix, the duck in clip time and the early end. The phase-close e2e run failed twice, for two unrelated reasons, neither of them the fixtures. "Adds a zoom effect" added a zoom at 0.2 s, before the two auto zooms; the autosave returned the effects sorted by start, and `setEffects(stored)` kept the selected index, so the selection (and Shift+Tab's target) moved to the 13 s zoom. The trace shows the save landing during the axe scan with request order [5.4 s, 13.1 s, 0.2 s] and response order [0.2 s, 5.4 s, 13.1 s]. The editor now maps the selection to the stored order. The isolation test pressed Ctrl+K right after `goto("/")`, which resolves on load about 16 ms before React attaches the hotkey listener, so the press was lost; a probe showed the first press failing and a second one opening the palette every time, and tracing slowed things enough to hide it. The test now retries the press with `toPass()`. The fix-wave gate also caught the golden path failing about one run in six: right after a reload, React's streamed segment (`<div hidden id="S:0">`) briefly held a second copy of the editor, so `getByTestId("clip-status")` hit strict mode; it now reads the pill inside `main`, as the music test already did. The `FIXTURES_VERSION` bump was reverted: `needed()` already creates the missing tone fixture without regenerating the rest. Parked: the upload list is lifted into `ClipEditor`, so the preview is silent for a moment after an upload; decimal typing in the number inputs; the caption-preview constants could be passed as props; the waveform can end flat, or the fade start late, when ffprobe's duration drifts; `clipsUsing` scans jsonb without an index; the transcript is loaded even when `trackId` is null; an upload's XHR isn't aborted when its button unmounts; the 50 MB limit is a literal in the copy; the envelope steps about 1.2 dB per frame on a ramp (add `asetnsamples` if zipper noise is heard); `trackTitleFromFile` duplicates `projectNameFromFile`; the no-cam music goldens are untested; lint scans `coverage/`; the render status check runs outside the save lock. Not verified: how YouTube's Content ID treats the mixed audio, and the Web Audio preview in a real browser. The tests use a fake `AudioContext`, and e2e Chromium plays no sound, so the preview hasn't been checked by ear in Chrome, Safari or Firefox (Safari's autoplay rules are the main risk).

## ADR-0069: Trending music from YouTube's chart

Context: people want to pick music the way the YouTube app's Shorts sound picker shows it, starting from what's trending right now. YouTube has no public API for the Shorts sound library or its trending list, and a song downloaded and mixed into the file is an unlicensed upload, not a Shorts sound, so it would draw Content ID claims, muting or blocks. Decision: the "Audio & text" tab lists the top 20 of the Data API's most-popular chart for the Music category (`videos.list?chart=mostPopular&videoCategoryId=10`) as links to YouTube, with a note that the song is added in the YouTube app (download the clip, then Add sound). Nothing is downloaded or mixed. The call uses the connected channel's token and books 1 unit of the `list` quota. The region comes from the first `Accept-Language` tag with a two-letter region (`pt-BR` → BR), else US; there is no region setting. Charts are public, so they're cached in memory per region for an hour and shared by workspaces; a failure is remembered per workspace and region for 10 minutes so a broken token doesn't call YouTube on every load. The page passes the promise unawaited and the list reads it with `use()` under its own `Suspense`, so the editor renders without waiting on YouTube. Alternatives: downloading the chart's audio with the yt-dlp downloader into the music library (breaks YouTube's terms and gets Content ID claims), a royalty-free library with an API (safe to mix in, but not what's trending on YouTube), and scraping YouTube Music's charts page (no contract, breaks silently). Consequences: the chart is the most-popular music videos, which overlaps with but isn't the same as the Shorts sound picker's trending list. A process restart refetches. Not verified: the real chart through the API, and the app's Add sound flow for an uploaded clip.

Amended 2026-11-26: the separate trending list is gone. Trending songs are a group in the searchable track picker next to the library, and picking one saves `audioMix.youtubeSound` (video id, title, channel, thumbnail) so the clip remembers which sound to add. It's still not downloaded or mixed in. Typing filters the library and the 20 chart entries in the browser, ignoring case and accents. When that isn't enough, "Search YouTube for …" runs `search.list` in the Music category plus one `videos.list` for durations and views: 101 units booked up front against the 10,000 a day that publishing also uses, so it only runs on that click, never per keystroke, and results are cached per region and query for an hour.

## ADR-0070: Hostable on Vercel Pro, still self-hostable

Context: Nimbus runs as a single box: `next dev` plus a long-running worker, Postgres in Docker, media on the local disk under `DATA_DIR`, and ffmpeg, whisper.cpp and yt-dlp on the PATH. We want it deployable to Vercel Pro without giving up running it on our own machine. On Vercel, functions are request-scoped, have no shared disk, cap request bodies at 4.5 MB and don't ship our binaries. Vercel Daemons (public beta, read on 2026-11-25) run a fixed number of instances of a container built from a Dockerfile, production deployments only, linux/amd64, up to 4 vCPU / 8 GiB each, no persistent disk, SIGTERM with a configurable grace period (default 30 s, up to 3,600 s) on every production rollout, old and new instances overlapping briefly. Decision: the web app runs on Vercel functions and never spawns a binary. The worker runs from one Docker image (`Dockerfile.worker`) as a Vercel Daemon in production, under `docker compose` when self-hosted, or on the host with `pnpm dev`. Media lives behind `StorageAdapter`, chosen with `STORAGE_DRIVER`: `local` (today's disk layout, for development, tests and single-box self-hosting) or `s3` (any S3-compatible store: Cloudflare R2 or S3 when hosted, MinIO when self-hosted). The adapter stops handing out file paths; the worker gets a local copy of an input in a per-job scratch directory and puts finished files back, so the `local` driver costs nothing extra. Browsers upload straight to storage: the server signs an upload target (a presigned PUT for `s3`, a PUT route for `local`), the browser sends the file, and a completion action checks the bytes and creates the project or track. Media is served by redirecting to a short-lived signed URL when the driver has one, and streamed as today when it doesn't. Music probing and waveform peaks move from the upload request into a `probe_music` job. The worker records its ffmpeg capabilities and a heartbeat in Postgres, and the settings page reads that instead of running ffmpeg. yt-dlp cookies come from a file (`YTDLP_COOKIES`) or its contents in `YTDLP_COOKIES_TEXT` when there is no browser to read. Alternatives: Vercel Blob (native integration, but not S3-compatible, so self-hosting would need a second adapter and a second upload flow), a worker on Fly or Railway (works on Hobby, but a second platform to run), Vercel Workflows plus Sandbox per job (no always-on cost, but a rewrite of the queue and minutes of cold start per render), and a hosted transcription API instead of whisper.cpp (smaller image, per-minute cost; still possible later behind `Transcriber`). Consequences: Preview deployments have no worker, so jobs queue until a production worker or a locally running one picks them up. A production deploy interrupts running jobs; they retry from the start of the step, and `terminationGracePeriodSeconds` bounds the wait. Daemons bill provisioned memory while idle. The bucket needs CORS for the app's origin (PUT, GET, HEAD, `Range`). Existing local data moves with `pnpm storage:push`. Not verified: Daemon CPU time for a whisper large-v3 transcription and a 1080p render, whether Vercel accepts a 4.5 MB+ streamed export zip from a function, and R2 presigned PUT with a signed `Content-Length`.

Amended during implementation: the S3 driver keeps worker inputs in a shared cache under `SCRATCH_DIR/cache`, keyed by ETag and bounded by `SCRATCH_CACHE_BYTES`, so a render doesn't download its source again. `S3_PUBLIC_ENDPOINT` signs browser URLs when the browser reaches storage on another host than `S3_ENDPOINT` (MinIO inside compose). Migrations run only on production builds (`VERCEL_ENV=production`), so a preview never migrates the production database. Self-hosting moved to `docker-compose.selfhost.yml`, which keeps Postgres and the MinIO console off the host; its MinIO is Bitnami's frozen `bitnamilegacy` build because official images are no longer published, and it gets no security updates. Vercel Blob is not used.

Amended after the final review: on S3 the browser uploads with a presigned multipart upload straight to the final key, because a single PUT caps at 5 GiB and the upload limit is 20 GiB, and the old server-side copy from a temp key was long work in a request. `startUpload` mints the project or track id and starts the upload; parts are at least 64 MiB, grown to stay within 10,000; the browser asks for part URLs in batches of 16 (each signed for 1 h), PUTs four at a time, retries a part twice with a fresh URL and sends the ETags to `completeUpload`. The local driver keeps one PUT to `/api/uploads/[token]`, now written to the final key. Nothing is moved: completion assembles the parts, checks the size and that the first bytes match the claimed extension (a misnamed music file is now rejected instead of being renamed), and removes the object or aborts the upload on failure. The token carries `exp` (1 h, local PUT) and `completeBy` (24 h, part signing and completion). The sweep aborts multipart uploads older than 24 h and removes final keys whose row never appeared after 24 h. On worker shutdown, an interrupted job goes back to `queued` without using an attempt (`queue.release`), so a deploy no longer costs every running job one of its retries.

## ADR-0071: Per-clip caption switch and hand timing

Context: some clips read better without captions, and whisper's word times can lag the speech, so captions need fixing by hand like effects. Decision: `captionOverrides` gains `enabled` (unset follows the project) and `offsetMs` (±5 s), and each page override can carry `startMs`/`endMs` next to its optional `text`. Page times are stored before the offset, so "shift all" always moves every caption, including hand-timed ones. The editor shows captions as one timeline lane under the effects; the sidebar Captions tab keeps only the look. Alternatives: per-word timing (too fiddly for a lane this size) or an offset only (can't fix one stray caption). Consequences: timing edits are indexed by page like text edits, so changing words per caption or the trim drops them; deleting a caption is a text edit to empty and comes back with "Reset edits".

## ADR-0072: Multi-track clip timeline

Context: trim, effects, captions, on-screen text and music each had their own card with fixed rows, so nothing could overlap on purpose and nothing could be added beyond one text and one song. Editors like CapCut solve this with one timeline of tracks you add as needed. Decision: the clip editor gets one timeline (ruler, playhead and zoom shared by every track). Items gain a `lane`; a lane never holds two items at once, and overlap means another lane of the same type. For effects of the same kind on two lanes the upper lane wins at render. Captions keep the transcript lane (index-based page edits, shift all) and gain captions added by hand plus extra caption lanes, each with its own screen height. `text_overlay` becomes `text_overlays`, a list with start and end, and `audio_mix` holds a list of music clips (start in the clip, in-point in the song, volume, fades) next to the original audio's volume and mute; migration 0021 converts stored rows. Trimming stays where it was in the data: the video track's edges move the clip's start and end. Alternatives: a free-form timeline document replacing every column (one big migration, and the render step would have to be rewritten at once) or keeping cards with more rows (doesn't give overlap or ordering). Consequences: effects without a lane are packed into lanes on save, so old clips keep their look; trimming still resets transcript caption edits and auto effects, while hand-added captions, texts and music keep their clip times and are cut at the new end.

## ADR-0073: A layout per clip

Context: the layout was set once per project in a "Layout & captions" step that blocked review and render until confirmed, with presets per resolution to skip it next time. A recording's framing can change between highlights (a moved webcam, a menu, a different game), and people want to frame each clip on its own. Decision: `clips.layout` (not null) is the only layout. A new clip starts from the workspace default in Settings › Layout (mode and webcam position, `cam-top` on top by default; portrait and square sources start as `no-cam-blur-fill`) with no webcam box. The clip editor runs the existing browser detection on 8 frames inside the clip's range the first time a clip whose mode uses the webcam has no box, applies it with `withDetection` (a found webcam keeps the clip's mode and position; none switches to `no-cam-blur-fill`) and autosaves it, which re-plans an un-edited effect track. "Find webcam" on the Layout tab runs it again. Until the box is set, `renderableLayout` renders and previews a webcam mode as `no-cam-fill`, and planned effects have no webcam focus. The `awaiting_layout` status, the `layouts` and `layout_presets` tables, the layout page and its project caption section are removed; the project caption style still comes from the workspace and each clip changes its own in the editor. Migration 0022 fills `clips.layout` from the clip override, else the project layout, else the fill layout, drops both tables and moves `awaiting_layout` projects to `ready_for_review`. The column defaults to the fill layout so a clip inserted without one still renders; every code path that creates clips sets it explicitly. Alternatives: detecting once per project and seeding every clip (one detection, but the same box for clips where the webcam moved), detecting only on request (clips rendered without a visit would never get a webcam), or running detection in the worker (needs MediaPipe in the worker image). Consequences: clips rendered without ever being opened have no webcam region; opening one changes its layout and marks a rendered clip out of date. A manual "Find webcam" uses the trim on screen. Resolution presets are gone; the workspace default replaces them. The legacy SQLite import no longer carries layouts.

## ADR-0074: The clip editor is a full-screen workspace

Context: the clip editor was a page inside the app shell, reached through a player dialog that opened first when a clip was clicked. The v2 design (`~/Downloads/nimbus-clip-editor-v2/design/`) makes it a fixed-height workspace: icon rail, top bar, stage, inspector and a timeline dock. Decision: the route moves to an `(editor)` route group with its own layout, so the URL stays `/projects/[id]/clips/[clipId]` and only this page drops the header and breadcrumbs to fill the height. The sidebar is the app's own `AppSidebar`, expanded or collapsed as the person left it; the design's fixed 56 px rail was built first and removed on request, since it took the collapse choice away on this one page. Clip tiles and the source strip link straight to it and the player dialog is gone; what it offered lives in the editor (approve and reject in the top bar, watch, download and publish in the Render button's menu, YouTube stats in Details). The rewrite is UI only: the edit payload, `updateClipAction` autosave, render and publish actions, webcam detection and the timeline model are the ones from ADR-0060, 0072 and 0073. Alternatives: a `usePathname` switch in the app shell (every page would carry the editor's layout code), or keeping the dialog as a quick preview (one more step before every edit, which is what was asked to go). Consequences: the inspector becomes a drawer under a 1180 px window whatever the sidebar's width, so with the sidebar expanded the stage is 204 px narrower than the design between 1180 and about 1380 px; a spoken caption can't be split, because its timing comes from the transcript; the Clips page no longer plays a clip larger than its tile, so checking a render means opening the editor; the editor needs 880 px of height and scrolls the page below that.

## ADR-0075: The timeline zooms on the wheel and pans from a handle

Context: the v2 editor (ADR-0074) listed every caption in the Captions tab and every effect in an Effects tab, next to the same items on the timeline, and the timeline scrolled sideways with the browser's scrollbar, opening a few seconds before the clip. Review asked for one place to edit each thing and for the timeline to behave like an editor's. Decision: the inspector keeps what applies to the whole clip (Details, Captions for style, on/off and timing, Layout); a caption or an effect is edited where it sits, in the timeline's popover, and planning effects again is in Add › Effect. The timeline opens with the clip's start at its left edge and hides the scrollbar. The wheel over the tracks zooms around the pointer, continuously between 5 and 320 px/s and never further out than the whole axis; a mostly sideways wheel or swipe pans. ## ADR-0076: Add on the track, and a dock that fills and resizes

## ADR-0079: An out-of-date yt-dlp is reported as that

Context: on 2026-11-27 every YouTube import failed with "YouTube still wants a sign-in", with valid cookies. yt-dlp 2026.10.26 could no longer read YouTube's player and got no formats for signed-in requests; the retry without cookies (which exists because signed-in requests sometimes get no formats) then hit the bot check, and its error replaced the real one. yt-dlp 2026.11.23 downloads the same video with the same cookies. Decision: when the retry without cookies fails too, the signed-in failure is the one reported. "Requested format is not available" and "No video formats found" map to `DEPENDENCY_MISSING` with a message to update yt-dlp, and doctor warns when the installed release is more than 21 days old (the version is its release date). The Dia export also skips partitioned cookies (`top_frame_site_key`), which belong to embeds on other sites and can't be expressed in cookies.txt. Alternatives: updating yt-dlp from Nimbus (it's installed by Homebrew or baked into the worker image, so Nimbus doesn't own it) or pinning a version (YouTube breaks old releases every few weeks). Consequences: a YouTube change can still break imports until yt-dlp ships a fix; the error now says so. The 21 days is a guess.

## ADR-0080: Retention rules from MrBeast's production handbook in the Claude prompts

Context: the selection, review and insights prompts were written from what we saw on our own streams. "How to succeed in MrBeast production" describes what that team learned from retention graphs. It is about 13-minute videos with a title and thumbnail, and says itself to apply it with a grain of salt. Decision: the parts that hold for a 15–60 s clip go into the three system prompts as fixed rules: title and hook are a promise the opening keeps, the strongest wording that is still true, a moment a stranger gets in one sentence, rarity over routine, things going wrong are content, no dull stretch, an abrupt end, variety across one list, no sponsor reads or sign-offs. A moment whose outcome is in doubt may start where the stakes are clear instead of on the payoff, since a withheld result is what the handbook credits for watch-through. The insights prompt learns how to read a retention curve and gets each clip's length. Left out: minute marks and the three- and six-minute re-engagements, click-through rate and thumbnails (a Short has neither a click nor a thumbnail in the feed), audience demographics, and everything about running a production. Alternatives: seeding these as playbook rules (the playbook holds only what a channel's own numbers showed and a person approved, and is capped at 12 per target) or a new scoring field per rule (nothing reads it). Consequences: the prompts are longer; the outcome-in-doubt exception can bring back slow starts if Claude applies it loosely, and the review's start is still limited to 8 s before the candidate. Not measured against real streams.

## ADR-0081: A clip can be joined from several parts of the recording

Context: a clip was one range of the recording. Compilations (every death, every bug), a setup with a payoff from twenty minutes later, and start/middle/end cuts couldn't be made. Decision: `clips.parts` holds an ordered list of ranges (`null` for one), and the clip gets its own timeline: it starts at the first part's start and lasts the sum of the parts, stored in `startMs`/`endMs`. Everything already placed in clip time (effects, caption edits, texts, music) stays on that timeline, so the editor, the preview and the filtergraph keep their code; only the source is different. Rendering opens the file once per part and concats them before the existing graph. The player maps between the timeline and the recording and jumps at each cut. Claude may return `parts` in the first pass; the review scores a joined clip as a whole and leaves its parts alone. Alternatives: a separate "compilation" entity made of clips (two editors, two render paths, and approval per piece that doesn't mean anything); effects and captions stored per part (every existing clip migrated, and an effect couldn't cross a cut). Consequences: parts can't overlap, so the same moment can't be shown twice in one clip (no replays); Claude only joins parts it sees in the same transcript chunk, so on a long stream a compilation spans at most one chunk; the browser preview seeks at each cut and may stall for a moment where the render doesn't; the waveform under a joined clip is built on the server, so it catches up with a part edit on the next load.

## ADR-0082: Whisper decodes each window without the previous text

Context: on multi-hour streams the transcript filled with one line repeated for minutes ("Tiremos quando estamos prontos." for seven minutes of a 13-minute stretch of a 10 h GTA 6 stream; 1,497 words where about 640 were spoken). whisper.cpp feeds the text of each 30 s window to the next as a prompt, so one hallucinated line over music or game noise is copied forward until clear speech breaks it, and the longer the recording the more often that happens. ADR-0046 hides these loops from captions and scoring, but the stored transcript, the transcript page and Claude's prompt still had them, and the real speech under a loop was lost. Decision: `-mc 0`, so a window never sees the previous one's text, and `-et 2.8` (default 2.4), so a window whose own text repeats fails the entropy check and is decoded again at a higher temperature. On the same stretch this left no loop, and the speech under it came back. Alternatives: `--vad` (a second model to download and check; not tried); `-sns` in place of `-et 2.8` (no loop either, but 13% fewer words on the same stretch); cutting the audio into chunks ourselves (the same effect as `-mc 0` with more code). Consequences: punctuation and capitalisation are a little less consistent across window borders, so some segments split on a pause instead of a full stop; a loop inside one window can still happen and is still dropped by `speakerWords`; transcripts made before this keep their loops until the project is transcribed again.

## ADR-0083: A landing page at the front door

Context: a signed-out visit to `/` went straight to the sign-in form, so nothing explained what nimbus does before asking for an account. A landing page was designed on the "Nimbus pages redesign" canvas in the heycamps language the app already uses. Decision: the page is `components/marketing/landing.tsx`, served by the static route `/welcome`; `proxy.ts` rewrites a signed-out `/` to it, so the address stays `/`, while every other signed-out path still redirects to `/login?next=…` and a signed-in `/` is still Projects. The hero is `HeroEdit`, a 14 s CSS-only loop of a clip being edited (no JavaScript, no video file, `cqw` units so it scales as one picture); each element's own style is its final state, so reduced motion shows the finished clip. Plan limits are read from `PLANS` and the language list from `components/settings/languages.ts`, so the page can't drift from the code. Only the Free plan is offered; Creator and Studio are shown with their limits and a "Soon" pill and no price, because billing isn't set up. The page frame in `docs/UX_PATTERNS.md` is for signed-in pages; this page follows `docs/DESIGN_SYSTEM.md` and the heycamps marketing rules instead (58 px nav, centred intros, one gradient phrase per chapter at most, the seal, the dotted horizon). Consequences: the gradient is now allowed in `landing.tsx` as well as the sign-in headline (the guideline check's allowlist says so); the page shows no testimonials, logos or usage numbers because there are none; example titles, the growth curve and the suggested rule are illustrations and labelled "Example" where a reader could take them for data; on a phone the hero stage scales down until its labels are too small to read, which is accepted for a decorative picture with a text alternative; `LANGUAGES` moved out of the `"use client"` module so a Server Component can read it.

## ADR-0084: One admin account

Context: ADR-0061 gave the Admin plan to every address ending in `@nimbus.dev`. Nimbus doesn't verify email addresses, so anyone could sign up with one and get a workspace without limits. Decision: the plan goes to `gabe@nimbus.dev` only (case-insensitive, exact match). Migration 0024 moves every other Admin workspace to Free. Supersedes the domain rule in ADR-0061; the plan itself is unchanged. Alternatives: an allowlist in the environment (more setup for one address); an admin flag set by hand in the database (nothing to restore it after a reset). Consequences: other team accounts are on Free and meet its limits once they are enforced; the address is still unverified, so the plan is only safe while that account exists and holds the address; adding a second admin is a code change.

## ADR-0085: Prices on the landing page, and a moving How it works

Context: ADR-0083 showed Creator and Studio with a "Soon" pill and no price, and How it works was four static cards. Decision: the landing page now prices the plans in reais: Free R$ 0, Creator R$ 67,69 a month, Studio "Custom". Creator is the recommended plan (raised card, lavender ring and glow, the page's primary button in that section). Studio shows "Custom" for the price and for every limit and its button is a `mailto:` link, because its terms are agreed per customer; the numbers in `PLANS.studio` stay as the default the code enforces. How it works is `StreamToClips`, a 12 s CSS-only loop of a three hour stream being read, nine moments marked, each turned into a vertical clip and then approved or rejected, over the four steps; the closing horizon's dots run along the arcs. Both follow the hero's rule: an element's own style is its final state, so reduced motion shows the finished picture. Supersedes the "only Free is offered" part of ADR-0083. Consequences: there is still no billing, so "Choose Creator" goes to sign-up and the account starts on Free; the price lives in `landing.tsx`, not in `PLANS`, until a checkout exists; the clips, scores and counts in the picture are illustrations.

## ADR-0086: The landing page moves when you scroll to it

Context: the hero and How it works loops started with the page, so by the time someone scrolled to How it works its 12 s story was somewhere in the middle, and the other chapters didn't move at all, with nothing leading from one to the next. ADR-0083 kept the page free of client JavaScript. Decision: one small client component, `InView`, marks an element `pending` or `seen` with an IntersectionObserver, and the stylesheet does the rest. A loop holds its first frame until 40% of its stage is on screen. Each chapter's heading, stage and lists rise in as they are reached; the editor's blocks land on the timeline, the chart draws and the suggested rule gets approved. Everything resets once it is fully off screen, above or below, so scrolling back to a chapter plays it again from the start, the hero included. Between chapters a thin amber playhead, the same one as in the hero and the editor, runs down the gap with the scroll (a CSS scroll timeline; where that isn't supported the line is just there). The attribute is only set once the script runs, so without it, and with reduced motion, the page is the finished picture as before. Supersedes the "no client JavaScript" part of ADR-0083. Consequences: content that waits is at opacity 0 until its observer fires, so anything new on the page that must never be hidden stays outside a `.cascade` wrapper; the thread is scrubbed by scroll while the reveals are timed, so they line up by placement, not by a shared clock.

## ADR-0087: Nimbus is for streamers and for clippers

Context: the landing page and the docs spoke to streamers only ("For streamers who record more than they post", "your stream", "your webcam"), and invariant 10 was titled "Only your own videos". People who clip other streamers' streams are as much the customer. Decision: the product is sold to both, with one offer: paste a YouTube or Twitch link, Nimbus selects and edits the clips, you can change anything, and the last word is yours. `docs/BUSINESS_LOGIC.md` opens with "Who it is for" and the wording rule that follows from it. The landing page leads with the link instead of a file, says "the stream" and "the webcam", names both audiences in the hero and answers the clipper's question in Questions. Invariant 10 is renamed "Only videos you have the rights to": the rule itself is unchanged (the import card already said "own or have the rights to use"), but it now says in words that someone else's stream with permission is a normal case. Consequences: Nimbus still doesn't check rights, and with clippers that matters more, so the permission line stays wherever a video is added; nothing in the app changed, since its copy already said "the streamer"; a channel's insights assume the clips on it come from Nimbus, whoever streamed them.
